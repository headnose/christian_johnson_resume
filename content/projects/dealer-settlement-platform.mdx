**Dealer Settlement Platform** is a personal learning project I'm building on my own after the BeaconFire training program. It models what happens after an auto loan closes: importing the loan, calculating what's owed to the dealer, generating a wire statement, and emailing it to the dealer and the dealer's bank. I'm using it to practice the parts of backend work my training didn't cover, like concurrency, Kafka, Redis, resilience patterns, security, and observability.

**Status:** in progress. This page only describes what's built and tested.

[View the code on GitHub](https://github.com/headnose/dealer-settlement-platform)

## What's built

- **Four Spring Boot services** in one multi-module Maven project: loan-service (a mock upstream), settlement-service (MongoDB), wire-service (MySQL), and notification-service
- **Concurrent loan import** with `CompletableFuture` on a bounded thread pool. Every loan gets its own result (Imported, Already imported, Not found, Not closed, or Failed), and re-imports never create duplicates
- **Settlement calculation** with `BigDecimal` money and adjustments, stored as one MongoDB document per loan with `Decimal128`, optimistic locking, and audit timestamps
- **Redis cache-aside** for settlement details
- **Wire generation and sending**: wire-service stores statements in S3 (SeaweedFS), publishes email requests to Kafka with `acks=all`, idempotent producers, and `min.insync.replicas`, and tracks delivery status
- **Email delivery** in notification-service with per-recipient idempotency keys in Redis (`SET NX`), so each recipient gets one email even if a message is delivered twice
- **Dead-letter topics and a delayed redrive job** that retries only recoverable failures, up to three times
- **Security**: role-based access (maker-checker) with Spring Security, user identity from a load balancer's signed claims header, and OAuth2 client credentials through Keycloak between services
- **Resilience4j circuit breakers** and timeouts on service calls, with logging when a breaker opens or closes
- **Observability**: Prometheus metrics and a Grafana dashboard, OpenTelemetry tracing in Jaeger, structured JSON logs, and an ELK stack where one search by loan ID finds the whole flow
- **Docker**: each service builds into a multi-stage, non-root image, and GitHub Actions builds and tests every pull request
- **A basic web UI** (nginx and one HTML page) for importing loans, calculating settlements, and generating and sending wires

## Load testing

I load-tested the platform with **k6** and used **Toxiproxy** to slow down or cut off S3 and Kafka. Before each run I wrote down what I expected, then compared it with what I measured. A few things I found:

- The real failure times didn't match the configured timeouts. The AWS SDK's retry limit cut retries short, and Kafka's `max.block.ms` decided when a send failed
- A send reported as failed could still publish its Kafka events, leaving the wire in Draft while the email went out. The fix is the outbox pattern, which is next on the list
- Starting the settlement-service call earlier and batching database inserts made wire generation measurably faster

## What I've Learned

Most of what I learned came from measuring instead of guessing. Running network calls in parallel is easy to start and harder to get right: I learned how a thread pool really grows, why each loan needs its own error handling, and why money belongs in `BigDecimal`. Load testing taught me that the timeout in a config file isn't always the timeout you get, and that "the request failed" doesn't mean nothing happened. That's the kind of gap that only shows up when you break things on purpose.
